#### GoF Criacional 1: VOD Transcodificação (Builder + Prototype)
 
> Escopo desta seção: **preparar o vídeo** para entrega, gerando MP4 (WebVideo) e HLS em várias resoluções. Usa as interfaces `IJob`, `IJobPrototype` e `IJobBuilder`.

##### Contexto (Problema)

Em uma plataforma de *Video On Demand* (VOD) como o PeerTube, os vídeos enviados pelos usuários precisam ser transcodificados para diferentes formatos e resoluções antes de serem disponibilizados para reprodução. No sistema modelado, o processamento de mídia atende a dois formatos de entrega:

1. **Web Video (MP4):** arquivo único otimizado para reprodução direta via HTTP.
2. **HLS (*HTTP Live Streaming*):** vídeo segmentado com arquivos de índice (`.m3u8`) e suporte a múltiplas resoluções para reprodução adaptativa.

A criação e execução dessas tarefas de transcodificação apresentam dois problemas de desenho de software:


- **Configuração de jobs com múltiplos parâmetros e formatos distintos:** criar tarefas de transcodificação envolve definir caminhos de entrada e saída, resoluções, limites de duração e tempos de segmentação. Fazer essa instanciação diretamente na classe `Video` gera alto acoplamento e construtores com muitos parâmetros. <a id="problema-configuracao-jobs"></a>

- **Geração repetitiva de resoluções para o mesmo vídeo:** para suportar streaming adaptativo ou diferentes qualidades (ex.: 1080p, 720p, 480p), o sistema precisa criar múltiplos jobs com os mesmos parâmetros base, alterando apenas a resolução alvo. Recriar cada job do início gera duplicação de lógica e validação.[¹](#ref1)[³](#ref3) <a id="problema-geracao-resolucoes">

Para resolver esses pontos, foram aplicados os padrões GoF Criacionais **Builder** e **Prototype**:

###### GoF Builder
- **Como é utilizado:** a interface `IJobBuilder` e suas implementações concretas (`WebVideoJobBuilder` e `HlsJobBuilder`) fornecem métodos para montar passo a passo instâncias de `JobWebVideo` e `JobHLS`. A classe `Video` atua como cliente ao invocar o builder por meio do método `solicitarTranscodificacao(builder: IJobBuilder)`.
- **Benefícios:**
  - Separa o processo de construção dos jobs de sua representação final. [¹](#ref1)[²](#ref2)
  - Elimina construtores sobrecarregados na instanciação dos jobs.
  - Permite criar diferentes tipos de saída (MP4 único ou pacote HLS segmentado) usando uma mesma interface de construção.
  - Facilita a extensão para novos formatos de transcodificação sem alterar a classe `Video`.

###### GoF Prototype
- **Como é utilizado:** a interface `IJob` estende `IJobPrototype`, exigindo a implementação do método `clone()` nas classes concretas `JobWebVideo` e `JobHLS`. No método `solicitarVariantesResolucao(jobPrototipo: IJob, resolucoes: String[])`, a classe `Video` recebe um job base já configurado, clona sua instância para cada resolução desejada e atualiza apenas a propriedade `resolucao` antes da execução.
- **Benefícios:**
  - Elimina a necessidade de reconstruir e revalidar todos os parâmetros do job (URL original, diretório de saída, durações) para cada resolução gerada. [³](#ref3)
  - Garante consistência entre todas as variantes de um mesmo vídeo, pois todas compartilham a mesma configuração base herdada do protótipo.
  - Reduz o acoplamento do método de geração de variantes, que opera sobre a interface `IJob` sem precisar saber qual classe concreta está sendo clonada. [¹](#ref1)

### Como os dois se complementam
O **Builder** monta o job base uma única vez (configuração completa); o **Prototype** o replica por resolução. Builder responde "*como montar*"; Prototype responde "*como copiar o que já está pronto*" [¹](#ref1)[²](#ref2)[³](#ref3).

##### Interfaces

###### Interface `IJobPrototype`
Arquivo: [`job-prototype.interface.ts`](../../../../backend/src/vod/interfaces/job-prototype.interface.ts)

A interface `IJobPrototype` constitui define o contrato do **Prototype**. Exige a presença da operação `clone()`, permitindo que qualquer tipo de tarefa de transcodificação gere cópias idênticas e desacopladas de si mesma, preservando o estado interno sem que o cliente precise conhecer a classe concreta instanciada.

```typescript
export interface IJobPrototype {
  clone(): IJob;
}
```

###### Interface `IJob`
Arquivo: [`job.interface.ts`](../../../../backend/src/vod/interfaces/job.interface.ts)

A interface `IJob` unifica as responsabilidades de Produto do padrão **Builder** e de Protótipo Concreto ao herdar de `IJobPrototype`. Ela padroniza o acesso e a mutação das propriedades fundamentais da tarefa e expõe a operação assíncrona `executarJob()`, que efetua o processamento real de mídia via FFmpeg. O método `setResolucao` desempenha papel crítico na reutilização via protótipo: após a clonagem, apenas a resolução alvo é ajustada, mantendo válidas as demais configurações base.

```typescript
export interface IJob extends IJobPrototype {
  // ... Getters e Setters ...

  executarJob(): Promise<string>;
  clone(): IJob;
}
```

###### Interface `IJobBuilder`
Arquivo: [`job-builder.interface.ts`](../../../../backend/src/vod/interfaces/job-builder.interface.ts)

Define as etapas universais de montagem que qualquer construtor de job de vídeo deve contemplar: redefinição do estado (`reset`), configuração de entrada (`setVideo`), definição de resolução (`setResolucao`), diretório de saída (`setOutputDir`) e produção final da instância (`build`).

```typescript
export interface IJobBuilder {
  reset(): void;

  // ... Setters ...

  build(): IJob;
}
```

###### Job HLS
Arquivo: [`job-hls.ts`](../../../../backend/src/vod/jobs/job-hls.ts)

Processa o vídeo original gerando a segmentação HLS em arquivos `.ts`, playlists secundárias por resolução (`index.m3u8`) e a lista mestre unificada (`master.m3u8`). Ao executar `clone()`, produz uma cópia independente de todas as listas de resolução e opções de segmentação, viabilizando a instanciação paralela de perfis sem interferência mútua.

```typescript
export class JobHLS implements IJob {
  private videoUrl: string = '';
  private resolucoes: string[] = ['720p'];
  private outputDir: string = './media/vod/hls';
  private duracaoSegundos?: number;
  private duracaoSegmento: number = 4;

  constructor(
    videoUrl?: string,
    resolucoes?: string | string[],
    outputDir?: string,
    duracaoSegundos?: number,
    duracaoSegmento: number = 4,
  ) {
    if (videoUrl) this.videoUrl = videoUrl;
    if (resolucoes) {
      this.resolucoes = Array.isArray(resolucoes) ? [...resolucoes] : [resolucoes];
    }
    if (outputDir) this.outputDir = outputDir;
    if (duracaoSegundos) this.duracaoSegundos = duracaoSegundos;
    this.duracaoSegmento = duracaoSegmento;
  }

  // ... Getters e Setters ...

  public async executarJob(): Promise<string> {
    // ... validação dos parâmetros e existência do vídeo de entrada ...
    // ... criação dos diretórios das variantes e iteração sobre as resoluções configuradas ...
    // ... execução do FFmpeg para segmentação (.ts) e sub-playlists (.m3u8) por resolução ...
    // ... geração da Master Playlist unificada (master.m3u8) com perfis multivariantes ...
    return masterPlaylistPath;
  }

  public clone(): JobHLS {
    return new JobHLS(
      this.videoUrl,
      [...this.resolucoes],
      this.outputDir,
      this.duracaoSegundos,
      this.duracaoSegmento,
    );
  }
}
```

###### Video
Arquivo: [`video.entity.ts`](../../../../backend/src/vod/entities/video.entity.ts)

A classe `Video` atua como o **Cliente** de ambos os padrões de projeto. Ela possui um papel duplo de orquestração:
1. **Consumidor do Builder (`solicitarTranscodificacao`):** Recebe qualquer implementação de `IJobBuilder`, solicita a construção da tarefa via `build()`, injeta o caminho do vídeo original caso necessário e executa a transcodificação sem precisar conhecer a classe concreta do job nem os detalhes operacionais de sua criação.
2. **Consumidor do Prototype (`solicitarVariantesResolucao`):** Recebe uma tarefa protótipo já configurada e uma coleção de resoluções pretendidas. Para cada resolução, invoca `clone()`, altera somente a resolução (`setResolucao`) e executa o processamento.
3. **Múltiplas URLs de WebVideo por Resolução:** A classe armazena internamente um `Map<string, string>` denominado `urlsWebVideo`. Dessa forma, à medida que cada resolução é transcodificada, seu endereço é catalogado pela chave correspondente. Isto não é necessário no caso da transcoficação *HLS* pois é gerada apenas uma playlist contendo todas as resoluções.

```typescript
export class Video {
  private videoOriginalUrl: string = '';
  private urlsWebVideo: Map<string, string> = new Map<string, string>();
  private urlHLS: string = '';

  constructor(videoOriginalUrl: string = '') {
    this.videoOriginalUrl = videoOriginalUrl;
  }

  // ... Getters e Setters ...

  public async solicitarTranscodificacao(builder: IJobBuilder): Promise<string> {
    const job = builder.build();

    if (!job.getVideoUrl() && this.videoOriginalUrl) {
      job.setVideoUrl(this.videoOriginalUrl);
    }

    const resultado = await job.executarJob();

    if (job instanceof JobWebVideo) {
      this.urlsWebVideo.set(job.getResolucao(), resultado);
    } else if (job instanceof JobHLS) {
      this.urlHLS = resultado;
    }

    return resultado;
  }

  public async solicitarVariantesResolucao(
    jobPrototipo: IJob,
    resolucoes: string[],
  ): Promise<string[]> {
    const resultados: string[] = [];

    for (const resolucao of resolucoes) {
      const jobClonado = jobPrototipo.clone();
      jobClonado.setResolucao(resolucao);

      const pathGerado = await jobClonado.executarJob();
      resultados.push(pathGerado);

      if (jobClonado instanceof JobWebVideo) {
        this.urlsWebVideo.set(resolucao, pathGerado);
      } else if (jobClonado instanceof JobHLS && !this.urlHLS) {
        this.urlHLS = pathGerado;
      }
    }

    return resultados;
  }
}
```

### Discussão crítica (GoF VOD Transcodificação)
 
- **Builder sem *Director*.** O GoF prevê, opcionalmente, um Director que encapsula a ordem de construção [¹](#ref1)[²](#ref2). Aqui o cliente (`transcode-target.ts`/`Video`) conduz as chamadas. Basta para o escopo, mas receitas repetidas (ex.: "perfil HLS 720/480/360") poderiam virar um Director.
- **Prototype sem registro de protótipos.** O GoF cita o *Prototype Manager* como variação [¹](#ref1); o subgrupo passa o protótipo como parâmetro, mais simples.
- **`setResolucao` no clone HLS.** Em `JobHLS` substitui a lista inteira por uma única resolução (comportamento coberto por `vod.spec.ts`); coerente com variantes, mas pode surpreender.
- **Custo x benefício.** O Builder exige configuração passo a passo; o Prototype reduz esse custo ao copiar. Combiná-los evita duplicação sem perder legibilidade [¹](#ref1)[²](#ref2)[³](#ref3).
- **Código gerado por IA.** Validado por testes automatizados e execução real; a conferência humana segue necessária.

### GoF Criacional 2: VOD Reprodução (Abstract Factory)

> Escopo desta seção: **assistir ao vídeo** já transcodificado, nos formatos WebVideo (MP4) e HLS. Usa as interfaces `IPlayerFactory`, `IPlayer` e `ICarregadorSegmentos`.

#### Contexto (Problema)

Depois de transcodificado pelo GoF Criacional 1, o vídeo fica disponível em dois formatos, e cada um é reproduzido de um jeito diferente:

1. **Web Video (MP4):** o player toca um arquivo único, baixado diretamente do servidor via HTTP.
2. **HLS:** o player lê a Master Playlist (`master.m3u8`), escolhe a resolução e baixa os segmentos `.ts`. Assim como no PeerTube, esses segmentos podem ser obtidos de outros espectadores (P2P), com o servidor como alternativa.[⁶](#ref6)

Isso gera um problema de desenho de software:

- **Criação de objetos de reprodução que precisam ser compatíveis entre si:** para assistir a um vídeo são necessários dois objetos que trabalham juntos: um **player**, que controla a reprodução, e um **carregador de segmentos**, que busca os dados do vídeo. Os dois dependem do formato, e misturá-los não funciona: um player WebVideo com um carregador P2P, por exemplo, falha, porque o MP4 não é segmentado. Se a classe `Video` instanciasse esses objetos diretamente, ficaria acoplada a todas as classes concretas e seria responsável por garantir que a combinação está correta.[¹](#ref1)[⁵](#ref5) <a id="problema-familias-reproducao"></a>

Para resolver esse ponto, foi aplicado o padrão GoF Criacional **Abstract Factory**:

##### GoF Abstract Factory
- **Como é utilizado:** a interface `IPlayerFactory` define a criação de uma família de objetos de reprodução (`criarPlayer` e `criarCarregador`). As fábricas concretas `WebVideoPlayerFactory` e `HlsPlayerFactory` criam, respectivamente, o par `WebVideoPlayer` + `HttpCarregadorSegmentos` e o par `HlsPlayer` + `P2PCarregadorSegmentos`. A classe `Video` atua como cliente no método `assistir(fabrica: IPlayerFactory)`, que devolve um `IPlayer` pronto para uso.
- **Benefícios:**
  - Garante que player e carregador sejam sempre compatíveis, porque a combinação é decidida em um único lugar, a fábrica.[¹](#ref1)[⁵](#ref5)
  - Isola o cliente das classes concretas: quem recebe o player usa apenas a interface `IPlayer` (`reproduzir`, `pausar`, `buscar`, `setResolucao`).
  - Facilita a extensão: um novo modo de reprodução (ex.: transmissão ao vivo) entra como uma nova fábrica com seus produtos, sem alterar as famílias existentes.
  - Acompanha a decisão real do PeerTube: o HLS usa P2P e o WebVideo usa HTTP direto.

##### Por que não outros padrões criacionais
- **Factory Method:** criaria apenas o player, sem garantir que o carregador combine com ele. O problema envolve uma **família** de objetos.[⁴](#ref4)
- **Builder:** o player tem poucas configurações. A dificuldade não está em montá-lo passo a passo, e sim em escolher o conjunto certo de objetos.
- **Prototype:** não há um objeto caro de configurar que valha a pena clonar, já que cada espectador recebe um player novo.

### Como os GoFs 1 e 2 se complementam
O **Builder** e o **Prototype** respondem "*como produzir* cada formato", e o **Abstract Factory** responde "*como consumir* cada formato". O resultado da transcodificação (`urlsWebVideo` e `urlHLS`) é a entrada da reprodução, e a `master.m3u8` gerada pelo `JobHLS` é lida pelo `HlsPlayer`.

###### Carregador P2P
Arquivo: [`p2p-carregador-segmentos.ts`](../../../../backend/src/vod/carregadores/p2p-carregador-segmentos.ts)

**Produto concreto B2.** Simula o P2P do PeerTube. Primeiro procura o segmento com outros espectadores conectados ao mesmo tracker. Se nenhum par tiver o segmento, baixa do servidor via HTTP e o anuncia para os próximos espectadores.

```typescript
export class P2PCarregadorSegmentos implements ICarregadorSegmentos {
  private trackerUrl: string;
  private fallbackHttp: HttpCarregadorSegmentos;

  public async baixarSegmento(url: string): Promise<string> {
    const anuncio = swarm.get(url);

    if (anuncio && anuncio.peerId !== this.peerId) {
      return anuncio.conteudo;               // 1. outro espectador tem o segmento: P2P
    }

    const conteudo = await this.fallbackHttp.baixarSegmento(url);  // 2. fallback HTTP
    swarm.set(url, { peerId: this.peerId, conteudo });             // 3. anuncia no swarm
    return conteudo;
  }
}
```

###### Video
Arquivo: [`video.entity.ts`](../../../../backend/src/vod/entities/video.entity.ts)

A classe `Video` também é o **Cliente** do Abstract Factory. No método `assistir`, ela recebe uma fábrica, seleciona a URL do formato correspondente (gerada pelo GoF 1) e pede à fábrica um player pronto. A partir daí, quem chamou usa apenas a interface `IPlayer`.

```typescript
public assistir(fabrica: IPlayerFactory): IPlayer {

    : this.urlsWebVideo.values().next().value ?? '';

  return fabrica.criarPlayer(url);
}
```

### Discussão crítica (GoF VOD Reprodução)

- **Escolha da URL por `instanceof`.** Para seguir o diagrama, o `Video` identifica o tipo da fábrica para escolher entre `urlHLS` e `urlsWebVideo`, do mesmo modo que `solicitarTranscodificacao` faz com os jobs. Isso cria uma dependência do cliente com uma fábrica concreta. Uma alternativa seria a própria fábrica informar qual URL usa.
- **Novo produto exige mudar todas as fábricas.** Acrescentar outro produto à família (ex.: um gerenciador de legendas) obriga a alterar `IPlayerFactory` e todas as fábricas concretas. É a limitação conhecida do padrão,[¹](#ref1)[⁵](#ref5) aceitável aqui porque o par player + carregador é estável.
- **P2P simulado.** O `P2PCarregadorSegmentos` simula o swarm em memória. No PeerTube real, a troca acontece entre navegadores via WebRTC.
- **Código gerado com apoio de IA.** Validado por testes automatizados e execução real com os vídeos gerados pelo GoF 1; a conferência humana segue necessária.
